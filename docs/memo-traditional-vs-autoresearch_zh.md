# 传统AutoML vs Autoresearch方法论差异对比

**日期**: 2026-05-27
**主题**: 传统AutoML框架与autoresearch方法论的核心差异

---

## 概览

| 维度 | 传统AutoML | Autoresearch |
|------|-----------|-------------|
| **核心理念** | 超参数优化 + 架构搜索 | Program引导的agent驱动研究 |
| **搜索策略** | 贝叶斯、RL、进化算法 | 人类编写约束 + agent修改代码 |
| **评估方式** | 单目标/多目标指标 | 固定评估器 + 复合评分 |
| **代码可改性** | 黑盒优化器，用户控制配置 | 人类写约束，agent修改train.py |
| **迭代速度** | 每次实验分钟到小时级 | 快速迭代（5分钟周期） |
| **结果可复现性** | 基于配置 | Git版本控制实验 |

---

## 传统AutoML框架

**代表工具**: AutoGluon, TPOT, Auto-sklearn, H2O AutoML, NASBench

### 优势
- **效果经过验证**: 广泛应用于Kaggle竞赛、AutoML基准测试
- **搜索全面**: 贝叶斯优化、进化算法、强化学习
- **算法覆盖广**: 分类、回归、时间序列、推荐系统
- **生产就绪**: 企业级支持、部署工具、监控

### 局限性
- **黑盒调优**: 用户配置搜索空间，但底层算法不透明
- **单一目标**: 优化准确率/AUC，较少关注领域特定约束
- **领域无关**: 为通用表格数据设计，不专用于微生物组
- **无人介入**: 搜索过程中难以注入领域知识
- **计算密集**: 大搜索空间需要大量GPU/CPU资源

## Autoresearch方法论

**起源**: karpathy/autoresearch - 用于代码生成研究的轻量AutoML框架

### 核心设计
```
┌─────────────────────────────────────┐
│  program.md  ←  人类编写约束规则     │
├─────────────────────────────────────┤
│  train.py    ←  Agent可修改代码       │
├─────────────────────────────────────┤
│  prepare.py ←  固定评估器(不可变)    │
└─────────────────────────────────────┘
```

### 优势
- **透明约束**: program.md明确编码探索范围和禁区
- **人类介入**: 领域专家编写约束，agent探索方案
- **快速迭代**: 轻量级实验，git版本控制结果
- **领域适配**: 可直接编码生物/临床约束
- **多目标**: 性能+稳定性+生物相关性开箱即用

### 局限性
- **非完整AutoML系统**: 专注代码生成研究，非生产部署
- **算法支持有限**: 简单搜索(random)，无贝叶斯优化
- **手动结果追踪**: 依赖git做实验版本控制(无自动日志仪表盘)
- **无自动集成**: 不会自动组合多个模型
- **扩展性**: 设计为单节点执行

## 核心差异对比

### 1. 人类专家角色

| 传统AutoML | Autoresearch |
|-----------|--------------|
| 用户提供搜索空间 + 指标 | 专家编写program.md约束 |
| 人类无法中途干预搜索 | 人类可在迭代间调整约束 |
| 领域知识通过配置注入 | 领域知识编码为规则 |
| 专家角色：初始设置 | 专家角色：持续反馈 |

### 2. 搜索机制

| 传统AutoML | Autoresearch |
|-----------|--------------|
| 贝叶斯优化 (TPE, Parzen估计器) | 随机搜索 + agent探索 |
| 进化算法 (遗传编程) | Agent修改train.py代码 |
| 强化学习 (神经网络架构搜索) | Agent编写新代码策略 |
| 搜索空间在优化中固定 | 可通过program.md细化搜索空间 |

### 3. 评估理念

| 传统AutoML | Autoresearch |
|-----------|--------------|
| 固定评估函数 | prepare.py不可变(固定评估器) |
| 单目标 (准确率, AUC) | 复合评分: 性能+稳定性+生物相关性 |
| 测试集评估 | 交叉验证 + 稳定性追踪 |
| 验证集过拟合风险 | 显式稳定性度量对抗过拟合 |

### 4. 微生物组专项适配

| 维度 | 传统AutoML | Autoresearch |
|------|-----------|--------------|
| 特征选择 | 通用方法(无领域知识) | 领域感知策略 (LEfSe, ANCOM, LASSO) |
| 生物相关性 | 不考虑 | DomainMetrics.biological_relevance() |
| 特征稳定性 | 不测量 | CV折间Jaccard相似度 |
| 领域约束 | 难以注入 | program.md编码肠肺轴、体质规则 |

## 何时使用哪种

### 使用传统AutoML当:
- ✅ 处理标准表格数据(客户、金融、传感器数据)
- ✅ 需要生产级部署，最小化工作量
- ✅ 希望自动集成多个模型
- ✅ 领域专业知识有限，无法编写约束
- ✅ 需要贝叶斯优化或神经网络架构搜索

### 使用Autoresearch当:
- ✅ 处理专业领域(微生物组、基因组、临床)
- ✅ 希望显式注入领域知识
- ✅ 需要多目标优化+领域特定指标
- ✅ 规划人机协同研究工作流
- ✅ 探索算法设计空间，非仅超参数调优

## 混合方案推荐(微生物组场景)

```
┌──────────────────────────────────────────────────────┐
│           微生物组混合AutoML方案                       │
├──────────────────────────────────────────────────────┤
│  1. Autoresearch风格:                                  │
│     - program.md含微生物组约束                        │
│     - 多目标评分(性能+稳定性+生物相关性)               │
│     - 特征选择策略(LEfSe, LASSO)                      │
├──────────────────────────────────────────────────────┤
│  2. 传统AutoML风格:                                    │
│     - 贝叶斯优化(Optuna)调优超参数                     │
│     - AutoGluon风格集成最终模型                        │
│     - 生产部署流水线                                   │
└──────────────────────────────────────────────────────┘
```

### 实施路线

1. **阶段1**: 使用autoresearch探索(train.py迭代)
2. **阶段2**: 在表现最好的配置上应用贝叶斯优化(Optuna)
3. **阶段3**: 使用AutoGluon或自定义stacking集成最佳模型
